# 压力演示实测记录

作业在**独立子进程**中运行，峰值 RSS 由父进程在 Linux 下通过
`resource.getrusage(RUSAGE_CHILDREN).ru_maxrss` 测量（KiB 换算 MiB），即作业
进程自身的驻留峰值，不含生成器与校验器。输出文件另经流式校验：总行数、严格
`(left_row, right_row)` 排序、未匹配行 null 语义，全程不把输出读入内存。
数据为单一热门键场景：除少量冷行外，所有左/右热行共享同一个键，是
"工作量全挤在一个键上" 的最坏情形；生成器逐行写盘，从不展开 m×n 配对。

复现（规模全部可参数化；普通回归不要直接跑全规模）：

```bash
python3 -B -E scripts/stress_demo.py \
  --data-dir <dir>/data --work-dir <dir>/work --output <dir>/pairs.jsonl \
  --report <dir>/report.json
```

## 实测环境

* Linux 6.12.69 (aarch64, glibc 2.36)，CPython 3.11.2，仅标准库；
* 机器内存约 8 GiB；作业预算上限 96 MiB（超限脚本以非零码退出）。

## 数据点 1：全规模，输入 > 256 MiB（fan_in = 4）

| 项目 | 实测值 |
|---|---|
| 输入规模 | 左 307 行 / 右 14 行，合计 **257.5 MiB**（270,009,473 字节） |
| 热门键构成 | 左 300 行 × 右 8 行，单条左载荷约 900,000 字节 |
| 输出行数 | **2,407 行**（2400 配对 + 7 条未匹配左行），2.06 GiB |
| 排序块设置 | `chunk_bytes=16 MiB`，`chunk_size=100000`（实际由字节预算主导） |
| 扇入 | **4** |
| 落盘段数 | 左 16 段 / 右 1 段 |
| 归并轮数 | 左 2 轮、配对 4 轮 |
| **作业峰值 RSS** | **31.34 MiB**（预算 96 MiB，达标，余量约 65 MiB） |
| 墙钟时间 | 57.66 s |
| 输出校验 | 行数、排序、null 语义全部通过 |

归档：`stress_results/stress_257mib_fanin4.json`

## 数据点 2：中等规模，强制小扇入与小字节预算（fan_in = 2）

| 项目 | 实测值 |
|---|---|
| 输入规模 | 左 67 行 / 右 12 行，合计 17.17 MiB |
| 热门键构成 | 左 60 行 × 右 6 行，单条左载荷约 300,000 字节 |
| 输出行数 | 367 行，103.05 MiB |
| 排序块设置 | `chunk_bytes=4 MiB` |
| 扇入 | **2**（最小档，段再多也不会同时打开全部段） |
| 落盘段数 | 左 5 段 / 右 1 段 |
| 归并轮数 | 左 3 轮、配对 5 轮 |
| **作业峰值 RSS** | **16.16 MiB**（预算 96 MiB，达标） |
| 墙钟时间 | 2.18 s |

归档：`stress_results/stress_17mib_fanin2.json`

## 结论

* 输入 257.5 MiB、输出 2.06 GiB 且单一键承担 2400 个配对时，峰值 RSS 仅
  31.34 MiB，远低于 96 MiB 预算；RSS 由块字节预算与解释器基线决定，与
  总行数、输出行数和最大同键组无关。
* 扇入降到 2 后归并轮数增多，但峰值 RSS 不升反降（16.16 MiB），印证
  "打开文件数与归并堆均受 `fan_in` 约束，不随段数增长"。
* 注：`chunk_bytes` 是按缓冲帧字节数计的软上限——单条记录本身必须能完整
  驻留内存（见 README "单条记录大小限制"）；本数据点单条最大载荷约
  0.9 MiB，远小于预算。
